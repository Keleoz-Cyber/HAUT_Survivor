# 《河南工业大学生存挑战》需求规格说明书

> 项目类型：Java 课程设计 / 校园模拟系统 / 游戏化成长管理平台  
> 推荐正式题目：**基于 Java 的高校校园生存挑战与成长管理系统设计与实现——以河南工业大学为例**  
> 推荐项目展示名：**河南工业大学生存挑战** / **HAUT Survivor**  
> 文档版本：V1.0  
> 适用对象：Java 课程设计、数据库课程设计、Java Web 课程设计、软件工程课程设计

## 1. 项目概述

### 1.1 项目背景

大学生活包含学习、社交、运动、消费、考试、社团、实习、课设等多种场景。很多大学生在实际生活中会遇到任务拖延、期末压力、作息不规律、社交与学习冲突、生活费管理困难等问题。

传统的任务管理系统、日程管理系统、学生信息管理系统大多偏工具化，使用过程较枯燥，缺少代入感和持续使用动力。因此，本项目尝试将“大学生活管理”与“游戏化模拟机制”结合，设计一个面向河南工业大学学生的校园生存挑战系统。

系统以河南工业大学校园生活为背景，将校园地点、学习任务、随机事件、属性成长、副本挑战、成就称号和结局评价结合起来，让用户在模拟挑战中体验大学生活中的选择与取舍。

### 1.2 项目定位

本项目不是单纯的娱乐游戏，也不是普通的信息管理系统，而是一个：

- 面向大学生的校园生活模拟系统；
- 具有任务管理功能的成长记录平台；
- 融合随机事件、属性成长和成就激励的游戏化管理系统；
- 以河南工业大学校园文化和大学生日常生活为背景的课程设计项目。

### 1.3 项目目标

系统目标包括：

1. 帮助用户以趣味化方式记录和管理学习、生活、运动、社交等任务；
2. 通过随机事件和选择结果模拟大学生活中的决策影响；
3. 通过属性成长机制让用户直观看到自身状态变化；
4. 通过副本挑战、称号成就和结局评价提升系统趣味性；
5. 通过后台管理实现事件、任务、副本、成就等内容的可维护；
6. 体现 Java 项目中常见的用户管理、数据库设计、业务逻辑、权限控制和数据统计能力。

### 1.4 当前开发决策

根据当前项目沟通结果，暂定以下开发方向：

1. 技术栈不受教师硬性限制，优先选择便于开发、展示、扩展和撰写报告的 Java Web 技术路线；
2. 项目按“Demo 基础版”和“完整版”两个阶段推进，先保证基础流程可演示，再逐步扩展副本、成就、报告和后台能力；
3. 管理员后台采用渐进式实现：基础版只维护核心演示数据，完整版再扩展为较完整的内容管理后台；
4. 校园背景主要采用河南工业大学莲花街校区，并允许使用真实地点名称，具体教学楼、食堂、宿舍区等名称后期继续补充；
5. 默认演示数据、校园事件、副本文案、成就称号和结局描述由开发者与辅助设计共同补充；
6. 课程设计报告后期单独整理，当前阶段优先完成需求拆解、系统设计和功能实现。

## 4. 用户分析

### 4.1 目标用户

本系统主要面向以下用户：

1. 河南工业大学在校本科生；
2. 希望以趣味方式管理学习和生活的大学生；
3. 需要进行任务规划、成长记录、期末复习、课设推进的学生；
4. 参与课程设计答辩的学生和教师。

### 4.2 用户角色

系统设置三类角色：

| 角色 | 说明 |
|---|---|
| 普通用户 | 进行角色创建、校园挑战、任务管理、事件选择、查看成长报告 |
| 管理员 | 管理用户、地点、事件、任务、副本、成就、公告和系统数据 |
| 游客/未登录用户 | 只能访问登录注册页面或项目介绍页面 |

### 4.3 用户痛点

| 痛点 | 系统解决方式 |
|---|---|
| 普通任务管理枯燥 | 使用副本、称号、属性成长增强趣味 |
| 学习生活难平衡 | 用学业、健康、金钱、社交、压力等属性进行模拟 |
| 期末和课设压力大 | 设计期末周副本和 Java 课设副本 |
| 缺少持续动力 | 通过经验、等级、成就、结局刺激持续使用 |
| 普通课设缺少创新 | 将管理系统和校园模拟游戏结合 |

## 5. 系统总体描述

### 5.1 系统核心玩法

用户登录后创建一个“工大学生角色”，进入校园地图。系统根据用户选择的地点、当前周次、角色状态和随机概率触发校园事件。用户对事件作出选择后，系统改变角色属性，并记录事件结果。

用户还可以接受任务、挑战副本、获得称号、查看成长报告。学期结束或达到一定条件后，系统根据用户属性生成阶段性结局。

### 5.2 系统核心循环

系统核心循环如下：

1. 用户登录系统；
2. 创建或进入角色；
3. 查看当前属性状态；
4. 选择校园地点或进入任务页面；
5. 系统触发随机事件或用户接受任务；
6. 用户做出选择或完成任务；
7. 系统更新属性、经验、金币、压力等数值；
8. 判断是否获得成就或称号；
9. 生成成长记录；
10. 达到学期结束条件后生成结局评价。

### 5.3 系统边界

本系统主要实现模拟与管理功能，不包含以下复杂能力：

- 不实现大型 3D 游戏地图；
- 不实现真实 GPS 定位；
- 不实现真实学校教务系统对接；
- 不实现真实支付功能；
- 不强依赖 AI 大模型；
- 不强制使用真实校园建筑照片或校徽素材。

## 7. 详细功能需求

## 7.1 注册登录模块

### 7.1.1 功能描述

用户通过账号、密码注册系统。登录成功后进入主界面。

### 7.1.2 功能需求

1. 用户可以注册账号；
2. 用户名不可重复；
3. 密码需要进行基本校验；
4. 用户可以登录系统；
5. 登录失败需要给出提示；
6. 用户可以退出登录；
7. 管理员账号可进入后台管理页面。

### 7.1.3 输入输出

输入：

- 用户名；
- 密码；
- 确认密码；
- 昵称。

输出：

- 注册成功/失败提示；
- 登录成功/失败提示；
- 当前用户信息。

### 7.1.4 业务规则

1. 用户名长度建议为 4 到 20 位；
2. 密码长度建议不少于 6 位；
3. 同一用户名不可重复注册；
4. 普通用户和管理员通过角色字段区分。

## 7.2 角色创建模块

### 7.2.1 功能描述

用户首次登录后需要创建自己的校园角色。

### 7.2.2 角色信息

| 字段 | 说明 |
|---|---|
| 角色昵称 | 用户自定义 |
| 年级 | 大一、大二、大三、大四 |
| 专业方向 | 计算机、食品、机械、经管、通用等 |
| 成长路线 | 考研、就业、保研、竞赛、六边形、摆烂求生 |
| 当前周次 | 默认第 1 周 |
| 当前等级 | 默认 1 级 |
| 当前经验 | 默认 0 |

### 7.2.3 初始属性

默认初始属性可以设置为：

| 属性 | 初始值 |
|---|---|
| 学业值 | 60 |
| 健康值 | 70 |
| 金钱值 | 80 |
| 社交值 | 50 |
| 技能值 | 40 |
| 压力值 | 30 |
| 自律值 | 50 |

不同成长路线可以影响初始属性。

例如：

| 路线 | 属性调整 |
|---|---|
| 考研路线 | 学业 +10，自律 +5，社交 -5 |
| 就业路线 | 技能 +10，社交 +5，学业 -5 |
| 竞赛路线 | 技能 +15，压力 +5 |
| 六边形路线 | 各项较均衡 |
| 摆烂求生路线 | 压力 -10，自律 -10，社交 +10 |

## 7.3 属性面板模块

### 7.3.1 功能描述

属性面板用于展示角色当前状态，是系统的核心数据展示区域。

### 7.3.2 属性说明

| 属性 | 说明 | 范围 |
|---|---|---|
| 学业值 | 反映课程学习和考试状态 | 0-100 |
| 健康值 | 反映作息、运动、饮食状态 | 0-100 |
| 金钱值 | 反映生活费和消费状态 | 0-100 |
| 社交值 | 反映同学、室友、社团关系 | 0-100 |
| 技能值 | 反映编程、项目、竞赛、证书能力 | 0-100 |
| 压力值 | 反映考试、DDL、熬夜带来的压力 | 0-100 |
| 自律值 | 反映任务完成率和行为习惯 | 0-100 |
| 经验值 | 反映角色成长进度 | 不限 |
| 等级 | 根据经验计算 | 1 级起 |

### 7.3.3 属性边界规则

1. 除经验外，属性值最低为 0，最高为 100；
2. 压力值越高代表状态越差；
3. 健康值低于 20 时触发健康预警；
4. 压力值高于 80 时触发压力预警；
5. 金钱值低于 20 时触发生活费告急提醒；
6. 学业值低于 30 时触发学业风险提示。

## 7.5 随机事件模块

### 7.5.1 功能描述

随机事件是系统趣味性的核心。用户进入某个地点后，系统根据事件类型、触发概率、当前周次和角色属性随机选择一个事件。

### 7.5.2 事件类型

| 类型 | 示例 |
|---|---|
| 学习类 | 老师点名、课堂提问、小测、作业 DDL |
| 生活类 | 食堂排队、快递、宿舍卫生、生活费不足 |
| 健康类 | 体测、熬夜、运动、饮食 |
| 社交类 | 社团招新、室友邀请、班级聚餐 |
| 技能类 | Java 报错、项目实践、竞赛报名 |
| 特殊类 | 期末周、电脑蓝屏、灵感爆发 |

### 7.5.3 事件结构

每个事件应包含：

| 字段 | 说明 |
|---|---|
| 事件名称 | 如“早八点名危机” |
| 事件描述 | 展示给用户的剧情文本 |
| 事件地点 | 教学楼、宿舍等 |
| 事件类型 | 学习、生活、社交等 |
| 触发概率 | 0-100 |
| 触发周次 | 可限制在某些周次 |
| 是否启用 | 管理员控制 |
| 备注 | 可选 |

### 7.5.4 事件选项

每个事件至少包含 2 个选项，建议 3 个选项。

事件选项需要避免写成单纯的“正确选择、普通选择、错误选择”。更好的设计是让每个选项都有动机、收益和代价：

1. 短期舒服但长期吃亏，例如继续睡觉会恢复健康，但降低学业和自律；
2. 短期痛苦但长期收益，例如熬夜修 Bug 会提升技能，但增加压力和健康风险；
3. 低风险低收益，例如稳妥完成基础任务，评价普通但不触发额外危机；
4. 高风险高收益，例如赌一把提前答辩演示，成功则获得高评价，失败则压力暴涨；
5. 社交型选择，例如找同学帮忙可能降低压力，但消耗人情或影响后续事件。

事件文案应尽量具备校园画面感，可以使用适度夸张、幽默和 DDL 氛围，但不要脱离大学生日常生活。选项名称应像用户正在采取行动，而不是抽象的“优秀/普通/失败”。

示例：

事件：**明天早八有小测，室友邀请你今晚开黑。**

| 选项 | 结果 |
|---|---|
| A. 拒绝开黑，认真复习 | 学业 +8，自律 +5，社交 -2，压力 -2 |
| B. 打两局再复习 | 社交 +5，学业 +2，健康 -3 |
| C. 通宵开黑 | 社交 +10，健康 -15，学业 -8，压力 +10 |

### 7.5.5 事件触发规则

1. 用户选择地点后可以触发事件；
2. 系统优先筛选该地点下启用的事件；
3. 根据当前周次进一步筛选事件；
4. 根据概率随机抽取事件；
5. 用户选择选项后，系统更新属性并记录事件；
6. 若属性达到成就条件，则触发成就。

## 7.7 副本挑战模块

### 7.7.1 功能描述

副本是由一组阶段任务、任务情境和结算规则组成的阶段性挑战。用户推进副本时，原则上不自由填写完成内容，而是在系统预设的情境中进行操作、选择或接受判定，系统根据任务结果推进副本进度。

这种设计可以避免用户自由输入导致系统无法校验完成情况的问题，也能让副本结果更容易被记录、统计和评价。不同副本任务可以采用不同完成形式，通过随机事件和属性判定增加不确定性和趣味性。

副本不应只是一组任务清单，而应成为 Demo 中最能体现“可玩性”的核心玩法。基础版至少需要做出一个短流程副本，让用户在 5-10 分钟内体验到目标、压力、选择、随机变化和结算评价。

### 7.7.2 情境驱动式任务机制

副本中的每个阶段任务由系统预设以下内容：

| 内容 | 说明 |
|---|---|
| 阶段任务名称 | 例如“设计数据库”“整理复习资料”“完成跑步训练” |
| 任务类型 | 决定任务采用单选、小测、随机事件、属性判定、普通确认或关键任务等形式 |
| 任务情境 | 用一段文字描述用户当前遇到的具体情况 |
| 完成方式 | 由系统预设，避免用户自由输入导致无法校验 |
| 结算规则 | 根据用户选择、随机结果、答题结果或属性判定生成任务结果 |
| 完成评价 | 可分为优秀完成、良好完成、普通完成、勉强完成、失败、跳过等 |

任务形式可以灵活设计，不需要固定为三档 A/B/C：

| 任务形式 | 说明 | 适用场景 |
|---|---|---|
| 单选策略 | 用户从若干处理方式中选择一种，系统按选项结算 | 项目设计、复习策略、面试应对 |
| 随机事件 | 进入任务后随机触发不同状况，用户根据状况处理 | 修复 Bug、期末突发状况、宿舍/食堂事件 |
| 判断/小测 | 用户回答判断题或选择题，系统根据正确率结算 | 粮食安全知识、Java 基础题、食品安全选择题 |
| 属性判定 | 系统根据当前技能值、自律值、压力值等判断任务结果 | 体测、熬夜赶工、项目攻坚 |
| 普通确认 | 对不重要的过渡阶段，用户点击完成即可推进 | 查看说明、领取资料、进入下一阶段 |
| 关键任务 | 同时结合选择、随机事件和属性判定，产生不同评价 | 数据库设计、核心功能开发、最终答辩 |

用户完成某个阶段任务后，系统立即完成以下操作：

1. 记录任务类型和用户操作结果；
2. 根据结算规则计算完成评价；
3. 更新角色属性；
4. 发放经验奖励；
5. 更新副本阶段进度；
6. 判断是否进入下一阶段任务；
7. 判断是否触发副本完成、失败、成就或称号。

#### 示例：Java 课设副本 - 设计数据库

任务情境：

```text
你准备设计 HAUT Survivor 的系统数据库。需求里包含用户、角色属性、校园地点、随机事件、任务、副本、成就和结局等内容。你会怎么做？
```

任务类型：关键任务。

可采用的完成方式：

| 完成形式 | 结算方式 |
|---|---|
| 单选策略 | 用户选择“先画 ER 图”“直接建核心表”“边开发边补表”等策略，系统按选项给出基础评价 |
| 属性判定 | 如果技能值和自律值较高，则数据库设计评价提升；如果压力值过高，则可能出现遗漏字段 |
| 随机事件 | 可能触发“需求临时变化”“发现表关系设计冲突”等状况，影响本阶段结果 |

结果说明：

- 优秀完成：副本进度顺利推进，后续开发 Bug 风险降低，技能和自律获得较高提升；
- 普通完成：可以继续推进，但后续可能需要补充字段；
- 勉强完成：可以进入下一阶段，但系统会记录“数据库设计不完整”，后续修复 Bug 阶段可能增加压力或触发额外补救任务。

### 7.7.3 Demo 副本可玩性原则

Demo 阶段的副本设计优先考虑“少而好玩”，不追求一次性实现所有副本。至少选择一个核心副本进行深度设计，要求如下：

1. 有明确目标，例如“在答辩前完成 Java 课设并尽量拿到高评价”；
2. 有阶段推进，不只是一次性选择；
3. 有压力或倒计时表现，例如 DDL 倒计时、压力值过高、健康值不足；
4. 有风险收益选择，不能所有选项都只是简单好坏；
5. 有随机事件，例如临时改需求、Bug 暴走、室友干扰、老师提前检查；
6. 有属性判定，例如技能值影响修 Bug，自律值影响复习效率，压力值影响判断失误；
7. 有至少 1 个轻量小游戏或交互小关卡；
8. 有通关结算，包括分数、评价、称号、属性变化和一句有记忆点的结局文案。

推荐 Demo 核心副本：**Java 课设：DDL 前夜**。

该副本可以作为基础版重点体验内容，围绕“课程设计即将答辩，项目还差关键功能”的情境展开。副本流程建议如下：

| 阶段 | 情境 | 玩法形式 | 结算重点 |
|---|---|---|---|
| 1. 需求风暴 | 老师突然强调系统要体现数据库设计和校园特色 | 单选策略 | 决定后续 Bug 风险和技能收益 |
| 2. 数据库拼图 | 表关系混乱，需要把用户、属性、事件、选项、副本串起来 | 轻量拼图/连线小游戏 | 根据完成度提升技能或增加补救任务 |
| 3. Bug 暴走 | 控制台连续报错，DDL 还剩最后一晚 | 随机事件 + 属性判定 | 技能值、自律值和压力值共同影响修复结果 |
| 4. UI 抢救 | 页面太像表格，需要快速加背景和场景感 | 单选策略 + 普通确认 | 决定界面评价和答辩观感 |
| 5. 答辩现场 | 老师询问系统亮点和数据设计 | 判断/小测 + 关键任务 | 生成最终评价和称号 |

该副本的结局示例：

| 结局 | 条件示例 | 文案方向 |
|---|---|---|
| 课设战神 | 总分高，技能和自律较高，压力未爆表 | 你把系统跑起来了，答辩时甚至还能演示随机事件 |
| 勉强过关 | 总分中等，关键阶段至少通过 | 代码能跑，页面能看，报告还能补 |
| DDL 幸存者 | 压力高但最终通关 | 人快没电了，但项目还活着 |
| 答辩沉默现场 | 关键任务失败或压力爆表 | 系统打开了，沉默也打开了 |

## 8. 业务流程设计

### 8.1 用户登录流程

```text
打开系统 -> 输入账号密码 -> 校验账号密码
    -> 成功：进入主界面
    -> 失败：提示错误信息
```

### 8.2 角色创建流程

```text
用户首次登录 -> 判断是否已有角色
    -> 无角色：进入角色创建页面
    -> 选择年级、专业、路线
    -> 初始化属性
    -> 进入校园地图
```

### 8.3 随机事件流程

```text
用户选择地点 -> 系统筛选该地点事件
    -> 根据周次和概率抽取事件
    -> 展示事件描述和选项
    -> 用户选择选项
    -> 更新属性
    -> 记录事件
    -> 判断是否触发成就
```

### 8.4 任务完成流程

```text
用户创建或领取任务 -> 任务进入待完成状态
    -> 用户点击完成
    -> 系统判断是否逾期
    -> 更新任务状态
    -> 发放经验和属性奖励
    -> 判断是否升级或获得成就
```

### 8.5 副本挑战流程

```text
用户选择副本 -> 查看副本介绍和任务链
    -> 接受副本
    -> 进入当前阶段任务
    -> 系统读取任务类型、任务情境和结算规则
    -> 根据任务类型执行单选策略、小测、随机事件、属性判定、普通确认或关键任务
    -> 用户进行选择、答题、确认或接受属性判定
    -> 系统记录操作结果、随机结果或判定结果
    -> 系统生成完成评价
    -> 更新属性、经验和副本进度
    -> 判断是否进入下一阶段
    -> 判断通关条件或失败条件
    -> 通关成功：发放奖励和称号
    -> 通关失败：生成失败记录和属性惩罚
```

说明：副本阶段任务不依赖用户自由填写完成内容。系统通过预设情境、任务类型和结算规则判断完成质量，因此更适合课程设计演示、数据统计和后台配置。

### 8.6 结局生成流程

```text
达到学期结束周次 -> 读取用户属性和历史记录
    -> 匹配结局规则
    -> 生成结局名称、评价、建议
    -> 保存结局记录
```

## 10. 核心规则与算法设计

## 10.1 属性更新规则

当用户完成任务或选择事件选项后，系统根据变化值更新属性。

伪代码：

```java
newValue = oldValue + changeValue;

if (newValue > 100) {
    newValue = 100;
}
if (newValue < 0) {
    newValue = 0;
}
```

压力值虽然也是 0-100，但压力越高状态越差。

---

## 10.2 等级计算规则

建议每 100 经验升一级，也可以使用递增规则。

简单规则：

```text
等级 = 经验值 / 100 + 1
```

进阶规则：

```text
升级所需经验 = 当前等级 * 100
```

---

## 10.3 随机事件抽取规则

基础算法：

1. 查询当前地点下所有启用事件；
2. 筛选当前周次可触发的事件；
3. 根据事件概率进行随机；
4. 返回一个事件；
5. 如果没有匹配事件，则返回默认事件。

伪代码：

```java
List<Event> events = eventDao.findByLocation(locationId);
List<Event> available = filterByWeek(events, currentWeek);

int random = new Random().nextInt(100) + 1;
for (Event event : available) {
    if (random <= event.getProbability()) {
        return event;
    }
}
return defaultEvent;
```

> 注意：如果多个事件都有概率，建议使用“权重随机”而不是简单概率判断。

---

## 10.4 成就触发规则

当用户完成任务、触发事件或更新属性后，系统检查是否满足成就条件。

示例规则：

```text
如果 Java 编程类任务完成数 >= 5，则获得“Bug 驯服师”
如果 图书馆地点访问次数 >= 7，则获得“图书馆钉子户”
如果 Java 课设副本通关，则获得“课设终结者”
```

---

## 10.5 结局判定规则

结局判定可以按优先级执行。

示例：

```text
如果 skill >= 85 且 Java课设副本通关，则结局为“课设战神”
否则如果 academic >= 80 且 health <= 25，则结局为“熬夜修仙人”
否则如果 academic >= 80 且 health >= 70 且 social >= 70 且 skill >= 70，则结局为“六边形工大学子”
否则如果 pressure >= 85 且 overdueTaskCount >= 5，则结局为“DDL 受害者”
否则为“平衡成长型选手”
```

---

## 10.6 成长报告生成规则

成长报告可根据历史记录统计生成：

| 数据 | 来源 |
|---|---|
| 完成任务数 | task 表 |
| 事件触发数 | event_record 表 |
| 属性变化 | player_attribute 和属性变化记录 |
| 获得成就数 | user_achievement 表 |
| 常去地点 | event_record 关联 event/location |
| 系统建议 | 根据最低属性或最高压力生成 |

建议规则：

```text
如果健康值最低：建议增加运动和休息任务；
如果压力值最高：建议减少 DDL 类任务，增加放松事件；
如果学业值最低：建议进入图书馆或学习副本；
如果金钱值最低：建议减少食堂夜宵、控制消费；
如果技能值最低：建议接受项目实践或 Java 练习任务。
```

## 11.4 随机事件页面设计

随机事件页面应具有剧情感和选择张力。页面不应只显示事件文字和按钮，而应突出情境、地点氛围、风险提示和选择后果。

页面建议包含：

1. 事件背景图或地点氛围图；
2. 事件标题和剧情描述；
3. 当前属性摘要，例如压力、健康、技能、自律；
4. 2-4 个操作选项，选项文案要像“行动”，不要像普通表单；
5. 选项可以显示部分后果预览，例如“可能降低压力”“有 Bug 风险”，关键后果可以隐藏；
6. 选择后展示结算动画或结果卡片，包括属性变化、经验、评价和后续影响。

示例：

```text
事件名称：早八点名危机

事件描述：
你昨晚赶 Java 课设到凌晨，醒来时手机显示 7:52。
群里有人发：“老师已经打开点名表了。”

选项 B：给室友发出求救信号
选项 C：赌一把，继续睡到自然醒
```

```text
你成功赶到教室，但整个人非常困。
学业值 +5，健康值 -5，压力值 +3。
```

#### 11.5.1 视觉素材原则

1. 每个核心地点至少配置一张背景图或氛围图；
2. 图片可以来自真实校园照片、统一风格生成图或半写实插画；
3. 不要求精确还原真实地图，但地点名称、校园氛围和学生生活场景要可信；
4. 图片应服务于场景表达，例如图书馆偏安静紧张，食堂偏热闹生活，实验室偏 DDL 和调试压力；
5. 避免所有页面都是白底表格，至少地图页、事件页和副本页要有明显视觉差异。

#### 11.5.2 轻量小游戏类型

小游戏只作为副本阶段或特殊事件中的短互动，不作为系统主体。推荐类型如下：

| 小游戏类型 | 说明 | 适用场景 |
|---|---|---|
| 数据库连线 | 将表和关系连接起来，模拟 ER 图设计 | Java 课设副本 |
| Bug 定位 | 在多条报错信息中选择最可能的错误原因 | Java 课设、实验室事件 |
| 复习优先级排序 | 将考试重点按优先级排序 | 期末周副本 |
| 体测节奏条 | 在合适区间点击，模拟跑步节奏控制 | 体测副本 |
| 食堂路线选择 | 在排队、预算、健康之间选择路线 | 食堂事件 |
| 答辩快问快答 | 2-3 道选择题，模拟老师追问 | Java 课设或实习面试副本 |

小游戏结算应与属性系统联动，例如技能值提高容错率，自律值增加时间，压力值过高会降低提示质量。即使小游戏失败，也应给出有趣结算，而不是简单提示“失败”。

## 12. 非功能需求

### 12.1 性能需求

1. 普通页面响应时间不超过 2 秒；
2. 随机事件触发响应时间不超过 1 秒；
3. 系统至少支持 50 个用户数据的正常运行；
4. 数据查询应避免明显卡顿。

### 12.2 安全需求

1. 用户必须登录后才能进入系统；
2. 管理员和普通用户权限分离；
3. 用户只能查看和修改自己的角色数据；
4. 密码不建议明文存储，至少应进行简单加密或哈希；
5. 后台管理接口应限制普通用户访问。

### 12.3 可维护性需求

1. 随机事件、任务、副本、成就应尽量存入数据库；
2. 不建议把所有剧情写死在代码中；
3. 属性变化规则应统一封装；
4. 管理员应能维护大部分展示内容。

### 12.4 可扩展性需求

后续可以扩展：

- 更多校园地点；
- 更多副本；
- 更多专业路线；
- 更多结局；
- 真实日程提醒；
- 数据可视化图表；
- 多人宿舍协作玩法；
- 校园排行榜。

### 12.5 易用性需求

1. 页面文字应清晰；
2. 操作流程应简单；
3. 重要属性变化需要明显提示；
4. 任务和事件描述应有趣但不过度复杂；
5. 系统应提供默认数据，方便演示。

## 13. 技术方案建议

### 13.1 推荐技术路线

由于当前课程未限制必须使用 Swing、JavaFX 或其他固定框架，本项目推荐优先采用 Java Web 技术路线：

| 技术 | 用途 |
|---|---|
| Java | 主体开发语言 |
| Spring Boot | 后端框架，负责 Web 页面、业务逻辑和接口 |
| MyBatis-Plus | 数据持久层，简化数据库 CRUD |
| MySQL | 数据库存储用户、角色、事件、任务、成就等数据 |
| Thymeleaf | 服务端页面模板，降低前后端分离复杂度 |
| Bootstrap / 自定义 CSS | 页面布局和基础视觉样式 |
| ECharts | 完整版中用于成长报告和统计图表 |
| Maven | 项目构建和依赖管理 |

优点：

- 更适合实现注册登录、后台管理、数据库 CRUD 和统计图表；
- 相比 Swing/JavaFX，更方便截图、录屏、答辩展示和后期写报告；
- 相比 Spring Boot + Vue 前后端分离，开发成本更低，项目结构更容易控制；
- 方便从 Demo 基础版逐步扩展到完整版。

需要注意：

- 页面交互不追求复杂动画，优先保证流程清晰和功能完整；
- 权限控制基础版可先手写登录拦截，完整版再视情况引入 Spring Security；
- 数据库表设计基础版可以适当合并，完整版再拆分优化。

---

### 13.2 备选技术路线

如果后续课程时间较短，或老师更偏向基础 Java 桌面程序，也可以退回桌面端方案：

| 技术 | 用途 |
|---|---|
| Java | 主体开发语言 |
| JavaFX | 图形界面 |
| MySQL | 数据库存储 |
| JDBC / MyBatis | 数据库连接与持久层 |
| Maven | 项目管理 |

优点：

- 更接近传统 Java 课程设计；
- 不需要部署 Web 服务；
- 单机演示较简单。

缺点：

- 后台管理、统计图表和多页面展示不如 Web 方案自然；
- 界面美观度和可扩展性相对有限；
- 后期撰写“完整管理系统”报告时说服力略弱。

---

### 13.3 当前采用方案

当前暂定采用：

> Spring Boot + MyBatis-Plus + MySQL + Thymeleaf + Bootstrap

完整版根据开发进度补充：

- ECharts：成长报告、数据统计；
- Spring Security：如需更规范的权限控制再引入；
- 前端组件库：如页面复杂度上升，可在后期少量引入。

## 14. 版本规划

### 14.1 Demo 基础版

基础版目标不是只做“功能能点通”的最小闭环，而是完成一段可以顺利答辩演示、且具有基础可玩性的短流程体验。用户登录后创建角色，进入莲花街校区行动地图，触发有场景感的随机事件，选择不同处理方式后产生属性变化，并至少体验一个核心副本或副本片段。

Demo 基础版应让用户在 5-10 分钟内感受到：

1. 自己正在校园场景中行动，而不是在普通后台系统中切换页面；
2. 不同地点有不同氛围、图片和事件类型；
3. 选择会产生后果，且后果不总是简单的好坏；
4. 属性值会影响后续事件或副本阶段；
5. 至少一个副本具有阶段目标、随机变化、轻量小游戏和结算评价。

基础版必须完成：

1. 用户注册、登录、退出；
2. 普通用户和管理员两类角色区分；
3. 学生角色创建，包括昵称、年级、专业方向、成长路线；
4. 属性面板，展示学业、健康、金钱、社交、技能、压力、自律、经验和等级；
5. 莲花街校区行动地图，至少包含教学楼、图书馆、宿舍、食堂、操场、实验室、社团活动区、快递站；
6. 地图、事件和副本页面具备基础视觉素材，例如背景图、地点图标、主题色或氛围图；
7. 随机事件触发，用户在不同地点可能遇到不同事件；
8. 事件选项选择，选择后展示结果，并修改角色属性；
9. 至少 10 个默认事件，其中至少 5 个事件需要具备较强剧情感或校园梗；
10. 至少 1 个 Demo 核心副本，推荐实现“Java 课设：DDL 前夜”的简化版；
11. 核心副本至少包含 3 个阶段，其中至少 1 个阶段使用轻量小游戏或小测；
12. 基础任务管理，支持用户创建任务、查看任务、完成任务和获得简单奖励；
13. 管理员维护核心事件数据，至少支持事件的新增、修改、删除、查询；
14. 默认演示数据，至少包含测试账号、默认地点、默认事件、默认任务和默认副本片段；
15. 数据保存到 MySQL，重启系统后关键数据不丢失。

基础版演示流程建议：

```text
注册/登录 -> 创建校园角色 -> 查看属性面板 -> 进入莲花街校区行动地图
    -> 点击实验室或图书馆 -> 触发有剧情感的随机事件
    -> 选择处理方式 -> 属性变化和结果评价
    -> 进入 Java 课设：DDL 前夜副本
    -> 完成阶段任务/小游戏/属性判定
    -> 获得副本结算、称号或失败评价
    -> 管理员维护事件或副本内容
```

基础版完成后，项目应可以作为课程设计 Demo 进行展示。演示重点不只是“系统功能完整”，还要体现“校园生活被游戏化建模”“选择产生后果”“副本有可玩性”。

### 14.2 完整版

完整版目标是在基础版闭环上增强“游戏化成长管理系统”的完整度，让项目更适合写报告和答辩展示。

完整版建议增加：

1. 副本挑战模块，支持期末周、Java 课设、体测、粮食守护者等主题副本；
2. 副本任务详情，每个副本包含任务目标、任务类型、任务情境、完成方式、结算规则和失败/完成条件；
3. 成就称号模块，根据任务完成数、属性变化、事件选择和副本结果触发称号；
4. 结局评价模块，根据学期末属性生成阶段性结局；
5. 成长报告模块，展示周报、月报或学期报告；
6. 数据统计图表，展示属性趋势、任务完成率、事件触发次数等；
7. 任务模板模块，管理员可配置系统推荐任务；
8. 管理员后台扩展 CRUD，逐步覆盖地点、事件、事件选项、任务模板、副本、成就、结局规则；
9. 默认内容素材扩充，包括更多校园事件、副本文案、成就称号和结局描述。

完整版演示流程建议：

```text
基础版完整流程 -> 接受副本挑战 -> 完成副本阶段任务 -> 解锁成就称号 -> 查看成长报告 -> 生成学期结局 -> 查看后台统计
```

### 14.3 管理员后台阶段规划

管理员后台不建议一开始做得过大，可以按以下顺序逐步扩展：

1. Demo 基础版：只实现用户查看、事件管理、事件选项管理；
2. 完整版第一阶段：增加地点管理、任务模板管理、副本管理、副本任务选项和结算规则管理；
3. 完整版第二阶段：增加成就管理、结局规则管理、数据统计；
4. 加强版：增加公告管理、排行榜管理、内容批量导入导出。

这样既能保证基础版按时完成，也能让后台功能服务于核心玩法，而不是一开始被大量 CRUD 拖慢进度。

### 14.4 加强版

可以额外增加：

1. 排行榜；
2. 数据图表；
3. 多校区地图；
4. 专业路线差异化；
5. 事件连续剧情；
6. 存档导出；
7. 主题皮肤；
8. 多人宿舍小队挑战。

## 17. 风险与解决方案

| 风险 | 影响 | 解决方案 |
|---|---|---|
| 内容太像游戏，老师觉得不正式 | 影响选题通过 | 报告中强调“校园成长管理”和“游戏化激励” |
| 功能过多做不完 | 影响交付 | 先完成基础版，再扩展副本和成就 |
| 真实地点资料不完整 | 校园代入感不足 | 先用莲花街校区通用地点完成基础版，后期逐步补充真实教学楼、食堂、宿舍区名称 |
| 事件内容不够丰富 | 趣味性不足 | 先设计 30 个事件，后续管理员可添加 |
| 数据库表较多 | 开发复杂 | 基础版先合并部分表，完整版再拆分 |
| 界面不好看 | 展示效果一般 | 使用卡片、进度条、Emoji、简洁配色 |
| 规则太复杂 | Bug 增多 | 将属性变化统一封装成工具类 |

## 24. 总结

《河南工业大学生存挑战》是一个兼具趣味性和完整性的 Java 课程设计项目。它以大学生日常生活为基础，通过随机事件、任务挑战、属性成长、成就称号和结局评价等机制，将传统任务管理系统包装成具有校园特色的成长模拟平台。

本项目具有以下优势：

1. 面向大学生，场景真实；
2. 以河南工业大学为背景，具有本校特色；
3. 功能模块充实，适合课程设计；
4. 不依赖复杂美术资源；
5. 技术实现难度适中；
6. 既有趣味性，也有管理系统的完整性；
7. 适合答辩展示和后续扩展。
